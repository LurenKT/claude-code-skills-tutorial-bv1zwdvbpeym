最简单的理解：先问清楚，再写成文档，再拆任务，再用测试做，最后定期整理架构。

这些技能的作用是让 AI 每次按同一条工程路线工作。你少花时间纠偏，代码库也更容易保持整洁。

不知道从哪里开始时，就按这条顺序走。

技能 01

grill-me：需求还没想清时，用它来追问你

参考时间：01:15

它解决的问题：你觉得自己已经说清楚了，AI 直接开写后才发现理解错了。这个技能会让 AI 一次只问一个问题，把隐藏决策问出来。

  1. 把你的粗略想法告诉 AI，例如“我要给课程后台加一个资料面板”。
  2. 运行 /grill-me，让 AI 按设计树追问。
  3. 每次只回答当前问题，不急着进入实现。
  4. 等问题都收敛后，再进入 PRD 或执行阶段。
实际操作案例

给文章编辑器加“右侧文档面板”

你先说：我想让左边保留聊天，右边出现可编辑文档。AI 会继续问：文档保存在哪里？哪些页面有这个面板？编辑失败怎么处理？移动端怎么显示？

提示词示例：我想给文章编辑页加右侧文档面板，请用 /grill-me 先问我问题，直到方案足够清楚再写计划。
技能 02

to-prd：把问清楚的内容写成需求文档

参考时间：03:54

它解决的问题：聊天里已经达成共识，但共识没有沉淀。PRD 把问题、目标、用户故事、已定决策写下来，让后续任务能引用。

  1. 先完成一轮 grill-me，拿到明确答案。
  2. 运行 /to-prd，要求 AI 总结成 PRD。
  3. 检查用户故事是否能验收，不清楚就继续补问。
  4. 把 PRD 保存成 GitHub Issue 或项目文档。
实际操作案例

把“文档面板”变成 PRD

PRD 里写清：为什么要加面板、用户进入页面后看到什么、文档什么时候保存、AI 写入文档时如何提示、失败后怎么恢复。

提示词示例：请把刚才讨论的文档面板整理成 PRD，包含问题陈述、用户故事、范围外内容和验收标准。
技能 03

to-issues：把大需求拆成能独立完成的小任务

参考时间：06:11

它解决的问题：PRD 说明了目的地，但还没有执行路线。这个技能把 PRD 拆成多个小 Issue，并标出依赖关系。

  1. 把 PRD Issue 或 PRD 文档交给 AI。
  2. 运行 /to-issues，要求按“纵向切片”拆任务。
  3. 先做最能暴露风险的任务，例如核心引擎或关键集成。
  4. 每个 Issue 都链接回父 PRD，方便执行者回看背景。
实际操作案例

拆“文档面板”PRD

可以拆成 4 个任务：纯函数编辑引擎、右侧面板外壳、AI 写入文档流程、编辑器开关与保存状态。第一个任务先验证核心数据结构。

提示词示例：请把这个 PRD 拆成 3 到 5 个可独立完成的 GitHub Issue，每个 Issue 都要有验收标准和依赖关系。
技能 04

tdd：先用测试钉住行为，再让 AI 写代码

参考时间：08:52

它解决的问题：AI 写代码很快，但没有反馈就容易跑偏。TDD 让它先写失败测试，再写刚好通过的代码，最后整理结构。

  1. 先确认要改的接口和行为。
  2. 让 AI 写一个失败测试，只覆盖一个行为。
  3. 再让 AI 写最小代码让测试通过。
  4. 测试通过后，检查是否需要重构。
实际操作案例

测试“应用文档编辑操作”

先测一个纯函数：输入旧文档和编辑指令，输出新文档。测试覆盖插入段落、替换标题、撤销失败操作。函数稳定后，再接界面。

提示词示例：请用 /tdd 实现文档编辑引擎。先写一个失败测试，再写实现，每次只推进一个行为。
技能 05

improve-codebase-architecture：定期找代码库里最难懂的地方

参考时间：11:58

它解决的问题：代码库越乱，AI 越难判断职责边界。这个技能让 AI 像资深工程师一样找混乱点，提出模块加深、接口收敛的机会。

  1. 让 AI 自然浏览代码库，记录哪里需要来回跳文件。
  2. 列出 3 到 5 个架构改善候选。
  3. 选一个候选，让多个方案互相比。
  4. 把推荐方案写成重构 RFC 或 GitHub Issue。
实际操作案例

整理“文档编辑”模块

如果保存逻辑、AI 写入逻辑、编辑器状态散在多个组件里，就把它们收成一个更深的模块：外部只调用少量函数，内部处理复杂状态。

提示词示例：请用 /improve-codebase-architecture 检查文档编辑相关代码，找出最值得加深模块的 3 个候选。
